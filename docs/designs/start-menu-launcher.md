## Problem Statement

ClaudeBG works, but it isn't *installed*. To use it you double-click
`ClaudeBGTray.exe` out of a git working tree, and opening Claude Desktop is a
separate act from starting the tray that manages its background. Nothing
registers with the Start Menu, so Windows Search can't find it at all.

Wanted: type `ClaudeBG`, press Enter, get Claude Desktop with the background on
and the tray running.

## What Makes This Cool

The background stops being a thing you *enable* and becomes a property of how
you open Claude. The whole patch is invisible plumbing whose only job is to make
one moment feel right — and right now that moment is preceded by navigating to a
repo folder.

The second-order win is bigger than the shortcut. Because the launcher runs at
the exact instant the patch state is knowable, it can notice that Claude
auto-updated into a new `app-<version>` folder and silently repair itself before
opening. `README.md:400` currently documents that repair as a chore the user
absorbs. It stops being a chore.

## Constraints

- **Per-user only.** `README.md` promises no administrator rights. The shortcut
  goes in `[Environment]::GetFolderPath('Programs')`
  (`%APPDATA%\Microsoft\Windows\Start Menu\Programs`), never the all-users one.
- **`-Restore` must stay literally true.** The README's headline promise is that
  `-Restore` "puts them back exactly." A shortcut left in the Start Menu breaks
  that sentence, so uninstall is part of this design, not a follow-up.
- **Nothing may duplicate `Get-ActiveAppDir`.** Learning
  `claude-desktop-windows-process-and-version-gotchas` (9/10): the active version
  folder is *not* the highest-numbered one, and `packages\RELEASES` is the only
  source of truth. `ClaudeBG.ps1:88` already implements this correctly. A second
  copy in another language will drift.
- **Process matching must filter by install path.** Same learning: several
  `claude.exe` processes on this machine are the Claude Code CLI at
  `~\.local\bin\claude.exe`. `Stop-ClaudeDesktop` (`ClaudeBG.ps1:109`) already
  filters on `$InstallRoot\*`; the launcher must reuse that filter, not
  `Get-Process claude`.
- **`-Patch` needs Node on PATH** (`npx asar`). Auto-heal therefore has a real
  failure mode on a machine without Node, and it must degrade to "open Claude
  unpatched and say why," never to "refuse to open Claude."
- **`ClaudeBGTray.exe` has no embedded icon.** It was built without
  `/win32icon` (`README.md:286`), and `MakeIcon` (`tray/ClaudeBGTray.cs:115`)
  draws its disc at runtime. A shortcut needs a real `.ico` file on disk.
- **Windows will not let a program pin itself** to Start or the taskbar. That has
  been blocked since Windows 10. Pinning stays a manual right-click.

## Premises

All four agreed during the session:

1. The problem isn't that the tray is hard to launch — it's that opening Claude
   and having the background on are two separate acts. That's why the entry
   launches Claude, not just the tray.
2. Doing nothing has a recurring cost: launching from a git working tree, plus a
   dead background after every Claude auto-update.
3. This is wiring, not machinery. `Get-ActiveAppDir`, `Start-ClaudeDesktop`,
   `Invoke-Patch`, the tray's mutex, `Notify`, and `MakeIcon` all already exist.
4. A `.lnk` is a new artifact, so it needs an uninstall path. Install and
   uninstall are one decision, not two.

## Approaches Considered

### Approach A: PowerShell-only launcher
`-Launch` and `-InstallShortcut` added to `ClaudeBG.ps1`; the `.lnk` targets
`powershell.exe -WindowStyle Hidden -File ClaudeBG.ps1 -Launch`. No C# recompile.
**Rejected:** `-WindowStyle Hidden` still blinks a console on most Windows 11
configurations, the Start Menu entry's identity is a script host rather than an
app, and the already-running MessageBox at `tray/ClaudeBGTray.cs:44` keeps firing
on every launch after the first. Those are exactly the two papercuts most likely
to make the shortcut quietly go unused.

### Approach B: Tray owns everything
The `.lnk` targets `ClaudeBGTray.exe`; new C# parses `RELEASES`, checks the
`.orig` pair, and launches `claude.exe` directly, shelling to PowerShell only
when a patch is actually needed.
**Rejected:** puts a second copy of the version-folder resolution into C#, which
is the single piece of logic this project's own learnings file flags as easy to
get wrong. It also contradicts the architecture note the codebase states about
itself at `tray/ClaudeBGTray.cs:7`.

### Approach C: Tray is the face, the script stays the brain — CHOSEN
The `.lnk` targets `ClaudeBGTray.exe` with a real `.ico`. At startup the tray
calls a new `ClaudeBG.ps1 -Launch` through the hidden-PowerShell helper it
already has. The script resolves the version, checks the `.orig` pair,
auto-patches if needed, and starts Claude.

## Recommended Approach

Approach C, because the auto-heal UX is already written.

`RunScript` (`tray/ClaudeBGTray.cs:243-280`) already spawns `powershell.exe` with
`-NoProfile -ExecutionPolicy Bypass`, `CreateNoWindow = true`, captures both
output streams, and then reports **balloon on success, dialog with the captured
output on failure**. That is precisely the "reapply automatically, but say so out
loud" behavior chosen in the session, and Approach C is the only option that
reuses it rather than reimplementing it.

Concretely:

**1. `ClaudeBG.ps1` gains `-Launch`.**
```
$appDir  = Get-ActiveAppDir                       # existing, RELEASES-aware
$patched = (Test-Path "$appDir\resources\app.asar.orig") -and
           (Test-Path "$appDir\claude.exe.orig")
if (-not $patched) { Invoke-Patch }               # existing
if (-not (Get-Process | ? { $_.Path -like "$InstallRoot\*" })) {
    Start-ClaudeDesktop -AppDir $appDir           # existing
}
```
The patch check is two file-existence tests. No Node, no `npx`, no
`@electron/fuses` — the slow probe in `Invoke-Status` is not needed here, and
using it would put several seconds of `npx` cold start in front of every launch.

**2. `ClaudeBG.ps1` gains `-InstallShortcut` / `-RemoveShortcut`.**
`WScript.Shell` COM writes `ClaudeBG.lnk` into the per-user Programs folder,
`TargetPath` = `ClaudeBGTray.exe`, `IconLocation` = the generated `.ico`,
`WorkingDirectory` = the repo folder (the tray resolves `ClaudeBG.ps1` relative
to its own `BaseDirectory`, so this is belt-and-braces). Release the COM object
explicitly. `-Patch` calls install; `-Restore` calls remove.

**3. The tray's two startup paths both become launchers.**
- First instance: after `EnsureSync()` and `Tray.Visible = true`, call
  `RunScript("-Launch", ...)`. Balloon and error dialog come for free.
- Second instance (`isFirst == false`): replace the MessageBox at
  `tray/ClaudeBGTray.cs:44` with a direct hidden `powershell.exe -Launch`, then
  exit. Typing ClaudeBG while it's already running brings Claude up instead of
  nagging. This second path must not use `RunScript`, which touches `Tray` and
  `Sync` that a second instance never initializes.

## Open Questions

- **Where does the `.ico` get written?** A real multi-resolution `.ico`
  (16/32/48/256) means assembling the ICONDIR / ICONDIRENTRY container by hand —
  roughly 40 lines of binary writing in either language, and the fiddliest part of
  this whole design. Two options: PowerShell redraws the disc and writes the
  container (duplicates the drawing from `MakeIcon`), or `ClaudeBGTray.exe` gains
  an `--export-icon <path>` argument that reuses `MakeIcon` directly (one copy of
  the drawing, but `Main` has to start parsing arguments). Leaning toward the
  tray flag.
- **Claude running but unpatched.** `Invoke-Patch` calls `Stop-ClaudeDesktop`, so
  `-Launch` will kill and relaunch a running Claude to repair it. Correct, but it
  should be visible in the balloon text rather than a surprise. Alternative: skip
  the repair when Claude is already up and heal on the next cold launch.
- **Node missing.** Confirm the intended fallback is "open Claude anyway,
  unpatched, and show the failure dialog" rather than blocking the launch.
- **`-Patch` re-running install every time** is idempotent and cheap, but it will
  silently recreate the shortcut if the user deliberately deleted it. Acceptable?

## Success Criteria

1. Type `ClaudeBG` in the Start Menu, press Enter: Claude Desktop opens with the
   background on, the tray icon appears, and **no console window flashes**.
2. Do it again while both are already running: the Claude window comes up, and
   **no dialog appears**.
3. After a Claude Desktop auto-update: the balloon says it's reapplying, the
   repair runs, Claude opens patched. No manual `-Patch`.
4. Run `-Restore`: the Start Menu entry is gone and searching `ClaudeBG` returns
   nothing.
5. On a machine without Node: Claude still opens, and the dialog explains why the
   background is off.

## Distribution Plan

The deliverable is two local files — `ClaudeBG.lnk` in the per-user Programs
folder and `ClaudeBG.ico` in `%APPDATA%\ClaudeBG`. `-Patch` is the install
channel, `-Restore` is the uninstall channel; both already exist and are already
what the README tells people to run. No CI/CD and no release artifacts: the repo
is distributed by clone, and `ClaudeBGTray.exe` is rebuilt with the single `csc`
line at `README.md:286`. The only new distribution obligation is documenting the
Start Menu entry in the "Day-to-day use" section (`README.md:131`) and adding
`ClaudeBG.ico` to the file table (`README.md:278`).

## What I noticed about how you think

- Your script header says **"KNOWN CONSTRAINTS (all empirically verified, do not
  'simplify' these away)"** (`ClaudeBG.ps1:29`). That parenthetical is written to
  a future reader who will be tempted — including future you, including an AI.
  Most people document what the code does. You documented what the code will be
  wrongly *assumed* to do.
- Given the choice between the launcher silently repairing itself and one that
  announces it first, you took the one that announces. That's the same instinct as
  **"None of this is hidden from you"** in your README — and that README also
  says, up front, "If that is not a trade you want to make, stop here." You built
  a tool that tells people not to use it. That's rarer than it sounds.
- You picked the boring icon over the live-wallpaper thumbnail, and the flashy one
  was the one I described as the "whoa" option. You'd already read the con

- `tray/ClaudeBGTray.cs:7` says **"All the real work lives in ClaudeBG.ps1."** You
